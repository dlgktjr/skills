# design-rationale — 설계 근거를 문서로 남긴다

주요 설계 선택은 비교한 대안과 이유를 함께 남겨, 나중에 코드를 읽는 사람(다음 세션의 나 포함)이
의도를 추적할 수 있게 한다. 입력은 `REQUIREMENTS.md` · `DECISIONS.md` · 코드 · 이번 작업의 대화다.

## A. README

아래 항목을 정리한다. 에이전트가 초안을 쓰고 사용자가 검토한다.

```markdown
## 개요                      (무엇을 · 누구를 위해 — 목표 한 문장)
## 실행 방법
## 구조                      (DECISIONS 의 결정마다 한 줄 — 왜 이 구조인가)
## 범위 밖으로 둔 것           (제외한 항목과 채택하지 않은 안 — 제외한 이유)
## 알려진 한계
## 작업 방식                  (직접 작성한 부분 · 위임한 부분 · 기각한 제안)
```

## B. RATIONALE.md

결과물의 주요 선택마다 **무엇을 · 어떤 대안 중에서 · 왜** 골랐는지 정리한다.
DECISIONS.md 가 결정 한 줄이라면, 이 문서는 그 결정이 코드의 어디에 어떻게 반영됐는지까지 잇는다.

```markdown
## R1 · <선택 한 줄>                         예) 저장은 단일 JSON 파일로 한다
- 위치:       파일:줄 (코드에서 이 선택이 드러나는 곳)
- 대안:       실제로 비교한 안들 — 각 안의 장단점 한 줄씩
- 선택 이유:   요구사항의 어느 항목 때문인가 (필수 항목 · 완료 기준 · 제약)
- 트레이드오프: 이 선택으로 포기한 것 · 생길 수 있는 문제
- 실패 조건:   어떤 입력 · 상황에서 실패하는가
- 재검토 조건: 어떤 요구가 생기면 이 선택을 바꿔야 하나
```

## 규칙

- **실제로 비교한 대안만 쓴다.** 대화나 DECISIONS.md 에 없는 대안을 나중에 덧붙이지 않는다.
  비교 없이 정한 것은 `대안: 비교하지 않음` 이라고 적는다.
- **에이전트 제안을 기각했거나 수정한 곳**이 있으면 한 항목으로 남긴다 — 제안 내용 · 기각한 이유.
- **검증 결과는 실제로 돌린 것만 쓴다.** 확인하지 않은 것은 `알려진 한계` 에 적는다.
- 사용자가 검토해 실제 의도와 다른 곳을 고친다. 근거가 불분명한 항목은 해당 코드를 함께 확인한 뒤 고친다.
- 항목은 주요 설계 분기 위주로 3~7개. 사소한 구현 세부는 쓰지 않는다.
