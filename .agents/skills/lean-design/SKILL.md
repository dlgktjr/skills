# lean-design — 설계안을 고르고, 작업 그래프로 구현한다

세 단계로 진행하고, 각 단계 끝에서 사용자의 확인을 받는다.

```text
① 설계안 비교 ──(사용자 선택)──▶ ② 작업 그래프 ──(사용자 승인)──▶ ③ 그래프 실행
```

**작은 변경에는 쓰지 않는다.** 수정 파일이 1~2개이고 설계 분기가 없으면 이 절차 없이 바로 구현하고
`AGENTS.md` 의 검증 규칙만 따른다.

입력은 `REQUIREMENTS.md`(또는 대화에서 정리한 목표 · 필수 항목 · 범위 밖 항목 · 완료 기준)다.
없으면 그것부터 사용자와 정리한다.

## 모델 배정

대부분의 작업은 **6.1 Sol** 로 한다. 아래처럼 덜 복잡한 작업만 **Terra** 로 한다.

```text
Terra    repo 읽기(구조 파악 · 파일 찾기 · 요약) · 문서화(README · 주석 · 변경 기록) ·
         배포(빌드 · 릴리스 스크립트) · SRE/devops(CI · 컨테이너 · 인프라 설정 · 모니터링)
6.1 Sol  그 밖의 전부 — 설계안 비교 · 요구사항 해석 · 핵심 로직 · 디버깅 · 검증 판정
```

- 둘 중 어디인지 애매하면 6.1 Sol 로 한다.
- `메인` 노드와 메인 세션의 일(설계안 비교 · 작업 그래프 · 검증)은 6.1 Sol 이다.
- ①에서 설계 전에 저장소를 파악해야 하면 탐색은 Terra 서브에이전트에 맡기고 요약만 받는다.

## ① 설계안 비교

1. 설계안 2~3개를 표로 비교한다. **가장 단순한 안을 반드시 하나 포함한다.**

   ```text
   | 안 | 구조 한 줄 | 충족하는 필수 항목 | 비용(시간 · 토큰) | 위험 | 포기하는 것 |
   ```

2. 권장안의 구성요소마다 범위를 점검한다. 하나라도 "아니오"면 그 구성요소를 뺀 안을 제시한다.

   ```text
   필수 항목의 어느 줄 때문에 있는가?
   실제로 발생하는 상황을 다루는가, 가정한 상황인가?
   지금 없으면 완료 기준 중 무엇이 실패하는가?
   ```

3. 권장안과 이유를 한 줄로 말하고 **멈춘다.** 사용자가 고르면 고른 안과 기각한 안을 `DECISIONS.md` 에
   한 줄로 남긴다 (`AGENTS.md` 의 형식 — 대안과 기각 이유 포함).

## ② 작업 그래프 — PLAN.md

고른 안을 노드로 나눠 `PLAN.md` 에 표로 쓴다.

```markdown
| 노드 | 목표 | 수정할 파일 | 의존 | 담당 | 모델 | 완료 기준 | 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| N1 | 데이터 스키마 · 로더 | src/data.py | - | 메인 | 6.1 Sol | `pytest tests/test_data.py` | 대기 |
| N2 | API 라우트 | src/api.py | N1 | 위임 | 6.1 Sol | `curl -s localhost:8000/health` → 200 | 대기 |
| N3 | UI 골격 | web/ | - | 위임 | 6.1 Sol | `npm run build` exit 0 | 대기 |
| N4 | 화면-API 연결 | web/src/api.ts | N2, N3 | 메인 | 6.1 Sol | 확인: 목록 화면에 데이터가 표시되는가 | 대기 |
| N5 | 배포 설정 | Dockerfile | N4 | 위임 | Terra | `docker build -t app .` exit 0 | 대기 |
```

- **노드 크기**: 완료 기준 하나로 끝났는지 판정할 수 있는 크기. 판정 문장이 둘 이상이면 나눈다.
- **의존**: 그 노드의 결과물이 있어야 시작할 수 있는 노드만 적는다.
- **같은 파일을 수정하는 노드끼리는 의존을 걸어** 동시에 돌지 않게 한다.
- **담당**: 핵심 로직 · 요구사항 해석이 필요한 노드는 `메인`, 범위와 완료 기준이 표의 한 줄로 충분한 노드만 `위임`.
- **모델**: 위 `모델 배정` 을 따른다. `메인` 노드는 항상 `6.1 Sol`, `위임` 노드는 repo 읽기 · 문서화 · 배포 ·
  SRE/devops 일 때만 `Terra`.
- **완료 기준**: 실행할 명령(종료 코드로 판정) 또는 `확인: <사용자가 볼 항목>` 한 줄.
- 표 아래에 실행 순서를 한 줄로 적는다 — 예) `N1, N3 (병렬) → N2 → N4 → N5`.
- 인증 · 결제 · 개인정보 · 데이터 삭제처럼 실수의 비용이 큰 노드가 있으면 표 아래에 적고,
  그 노드에 리뷰를 붙일지 사용자에게 묻는다. 기본값은 붙이지 않음이다.

표를 보여 주고 **멈춘다.** 사용자가 승인하거나 고친 뒤에 ③으로 간다.

## ③ 그래프 실행

검증은 실행의 일부다. 사용자가 따로 요청하지 않아도 노드마다 4번을 하고, 끝나면 7번을 한다.

1. **시작할 수 있는 노드**를 고른다 — 의존 노드가 모두 `완료` 인 노드.
2. 그중 `위임` 노드끼리 서로 의존이 없으면 **서브에이전트로 병렬 실행**한다.
   서브에이전트를 쓸 수 없는 환경이면 한 노드씩 순서대로 실행한다.
   서브에이전트는 그 노드의 `모델` 칸 모델로 띄운다. 모델을 고를 수 없는 환경이면 기본 모델로 돌리고
   노드 보고 줄에 그렇게 적는다.
   서브에이전트 프롬프트에는 그 노드 한 줄만 넣는다:

   ```text
   목표: <목표>
   수정할 파일: <파일> (이 밖의 파일은 수정하지 않는다)
   범위 밖: <REQUIREMENTS 의 범위 밖 항목 중 관련된 것>
   완료 기준: <명령> 이 exit 0 이어야 한다. 끝나면 바꾼 파일 목록과 명령 결과를 보고한다.
   ```

3. `메인` 노드는 서브에이전트를 쓰지 않고 메인 세션에서 구현한다. 작성 전에 접근 방식(자료 구조 · 경계 조건 ·
   오류 처리)을 한 문단으로 보여 주고 사용자의 확인을 받는다.
4. **노드가 끝날 때마다 메인 세션에서 직접 검증한다.** 서브에이전트의 "완료" 보고만으로 완료 처리하지 않는다.
   - **동작**: 완료 기준 명령을 다시 돌린다. `확인:` 노드는 사용자에게 실행 방법을 주고 답을 기다린다.
   - **범위**: 바뀐 파일을 확인한다 — git 저장소면 `git status --porcelain`(새 파일 포함)과 `git diff --stat`,
     아니면 최근 수정된 파일 목록. 그 노드의 `수정할 파일` 밖을 건드렸거나 새 의존성(패키지 · 설정 파일)이
     생겼으면 실패로 처리한다. 필요한 변경이었으면 사용자에게 묻고 표를 고친다.
   - 병렬로 돈 노드들은 작업 트리를 공유하므로 바뀐 파일을 노드별로 나눌 수 없다. 바뀐 파일 전체를
     그 노드들의 `수정할 파일` 목록과 대조해, 어느 목록에도 없는 파일이 있으면 해당 노드들을 함께 실패로 본다.
   - 노드마다 한 줄로 보고한다:

     ```text
     N2 · `curl -s localhost:8000/health` → 200 · 바뀐 파일: src/api.py · 범위 OK → 완료
     ```

5. `PLAN.md` 의 상태를 갱신한다 — `대기` · `진행` · `완료` · `실패: 원인 한 줄`.
6. **실패한 노드가 있으면 그 노드에 의존하는 노드를 시작하지 않고 멈춰** 사용자에게 원인과 다음 선택지
   (다시 시도 · 노드 수정 · 범위 축소)를 묻는다. 의존 관계가 없는 다른 노드는 사용자가 원하면 계속한다.
7. **모든 노드가 `완료` 면 마지막에 한 번 완료 기준 명령을 다시 돌린다** (회귀 확인 — 뒤 노드가 앞 노드를
   깨뜨렸는지 본다). `확인:` 노드와 오래 걸리는 명령(수 분 이상)은 제외하고, 제외한 것을 보고에 적는다.
   결과를 노드별 한 줄로 보고하고, 하나라도 실패하면 그 노드를 `실패` 로 되돌린다.

## 요구사항이 바뀌면

영향받는 노드만 다시 계획한다. 바뀐 노드와 그 노드에 의존하는 노드의 상태를 `대기` 로 되돌리고,
바뀐 표를 사용자에게 보여 준 뒤 승인을 받는다. 이미 `완료` 인 무관한 노드는 다시 돌리지 않는다.

## 하지 않는 것

- 사용자가 설계안을 고르기 전, 또는 작업 그래프를 승인하기 전에 구현을 시작하지 않는다.
- 요구 문서 전체나 여러 노드를 서브에이전트 하나에 한꺼번에 넘기지 않는다.
- 사용자가 고르지 않은 노드에 리뷰 전용 서브에이전트를 붙이지 않는다 — 판정은 완료 기준 명령과 범위 확인으로 한다.
